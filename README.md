# meta-impcas-epics

English | [简体中文](README.zh-CN.md)

PetaLinux layer for cross-compiling EPICS and running IOC applications on the
target.

It provides EPICS Base, the support modules needed by the BLM IOC, a process
server for supervising IOCs, and the classes a recipe needs to build and package
an IOC application with a per-instance console port.

This document is the getting-started guide. The topic documentation lives in
[`docs/`](docs/README.md).

## Recipes

| Recipe           | Version      | Installs to                                  |
|------------------|--------------|----------------------------------------------|
| `epics-base`     | 7.0.10       | `/opt/epics/base[-7.0.10]`                   |
| `epics-asyn`     | 4.46         | `/opt/epics/modules/asyn[-4.46]`             |
| `epics-autosave` | 6.0          | `/opt/epics/modules/autosave[-6.0]`          |
| `epics-asyn-scope-ioc` | 1.0 | `/opt/epics/iocs/asyn-scope-ioc[-1.0]`      |
| `procserv`       | master (`+git`) | `/usr/bin/procServ`                       |

`epics-asyn-scope-ioc` is an example and the template for the BLM IOC: it builds
asyn's own simulated oscilloscope test IOC. It is what the IOC documentation
refers to. `procserv` follows upstream master, so it is
rebuilt on each run and needs network access.

## Classes

| Class                    | Purpose                                                          |
|--------------------------|------------------------------------------------------------------|
| `epics-module`           | Cross-build a support module with EPICS' own build system.        |
| `epics-ioc`              | Build and package an IOC application (a `makeBaseApp` tree).      |
| `epics-ioc-systemd`      | Run an IOC under procServ, single instance or multi-instance.      |

## PetaLinux Integration

The following procedure adds this layer to an existing PetaLinux project.

### 1. Place the Layer

Place the layer under the PetaLinux project's `project-spec/` directory:

```text
my-petalinux/
└── project-spec/
    ├── meta-impcas-epics/
    └── meta-user/
```

Use a symbolic link during development if desired:

```bash
cd my-petalinux/project-spec
ln -s /path/to/meta-impcas-epics meta-impcas-epics
```

### 2. Add the Layer

From the PetaLinux project root, run:

```bash
petalinux-config
```

Open:

```text
Yocto Settings -> User Layers
```

Add:

```text
${PROOT}/project-spec/meta-impcas-epics
```

Save and exit. PetaLinux writes the layer to `build/conf/bblayers.conf`.

Check the generated layer list:

```bash
grep meta-impcas-epics build/conf/bblayers.conf
```

Do not commit `build/conf/bblayers.conf`; it is generated by PetaLinux.

### 3. Verify Layer Visibility

PetaLinux projects must first load their bundled Yocto environment. From the
PetaLinux project root, use the path provided by the project:

```bash
source components/yocto/layers/poky/oe-init-build-env build
```

Some PetaLinux releases use `layers/core` instead of `layers/poky`:

```bash
source components/yocto/layers/core/oe-init-build-env build
```

After sourcing this environment, raw `bitbake` and `bitbake-layers` commands
are available for inspection. Do not run them before sourcing the PetaLinux
project environment.

Run these commands in the shell where the PetaLinux Yocto environment is
active:

```bash
bitbake-layers show-layers
bitbake-layers show-recipes epics-base
```

The output must list `meta-impcas-epics` and recipe version `7.0.10`.

## Project Configuration

Configure the installation prefix in `project-spec/meta-user/conf/user.conf`:

```bitbake
EPICS_PREFIX = "/opt/epics"
```

The recipe selects the EPICS target architecture from `TARGET_ARCH`:

```text
aarch64   -> linux-aarch64
other ARM -> linux-arm
```

Override it explicitly when needed:

```bitbake
EPICS_TARGET_ARCH = "linux-arm"
```

Zynq-7000 uses `linux-arm`; ZynqMP uses `linux-aarch64`. Machine-specific overrides are also supported:

```bitbake
EPICS_TARGET_ARCH:my-zynq-machine = "linux-arm"
EPICS_TARGET_ARCH:my-zynqmp-machine = "linux-aarch64"
```

### Verify Expanded Configuration

```bash
bitbake -e epics-base | grep -E '^(EPICS_PREFIX|EPICS_TARGET_ARCH|EPICS_HOST_ARCH|SRCREV|DEPENDS|RDEPENDS)='
```

The recipe fixes `EPICS_HOST_ARCH` to `linux-x86_64`. PetaLinux/BitBake
provides the target cross-compiler, `${TARGET_PREFIX}`, and target sysroot
automatically; no SDK compiler path needs to be hard-coded.

## Add to the Root Filesystem

Choose one of the following methods.

### User Rootfs Configuration

Add these lines to `project-spec/meta-user/conf/user-rootfsconfig`:

```text
CONFIG_epics-base
CONFIG_epics-asyn
CONFIG_epics-autosave
CONFIG_procserv
CONFIG_epics-asyn-scope-ioc
```

Then open the rootfs configuration menu and confirm the packages are selected:

```bash
petalinux-config -c rootfs
```

### Image Install List

Alternatively, add this to `project-spec/meta-user/conf/user.conf`:

```bitbake
IMAGE_INSTALL:append = " epics-base epics-asyn epics-autosave procserv epics-asyn-scope-ioc"
```

Do not use both methods at the same time.

`epics-asyn-scope-ioc` depends on `epics-asyn` and `procserv`, so selecting it
pulls those in; `epics-autosave` is only pulled in by recipes that use it. Keep the explicit entries if you
want to build and inspect the individual packages.

## Build

Build a recipe on its own (faster than a full image while iterating):

```bash
petalinux-build -c epics-base
petalinux-build -c epics-asyn-scope-ioc
```

Then build the complete image:

```bash
petalinux-build
```

The first build fetches EPICS Base and the modules from GitHub. Network access
or a configured source mirror is required unless the sources are already present
in `DL_DIR`. `procserv` tracks master and is therefore fetched and rebuilt on
every run.

## Verify the Target Installation

After booting the target, verify:

```text
/opt/epics/base -> base-7.0.10
/opt/epics/base-7.0.10/bin/<target-architecture>/
/opt/epics/base-7.0.10/lib/<target-architecture>/
/opt/epics/modules/asyn -> asyn-4.46
/opt/epics/modules/autosave -> autosave-6.0
/opt/epics/iocs/asyn-scope-ioc -> asyn-scope-ioc-1.0
/etc/profile.d/epics.sh
/usr/bin/procServ
```

The target filesystem must not contain host-architecture directories such as
`bin/linux-x86_64/`. The full layout, including what an on-target development
setup provides, is described in [EPICS Base](docs/epics-base.md).

For the IOC application, see [IOC applications](docs/ioc.md). The short version:

```bash
systemctl enable --now 'epics-ioc@tapd01'
caget TAPD01:scope1:Waveform_RBV
```

## Troubleshooting

QA findings, build failures and target-side diagnosis are collected in
[Troubleshooting](docs/troubleshooting.md). The two most common ones:

* A `buildpaths` QA warning means a packaged file kept a build path. The classes
  scrub what they generate, so a new warning usually means a file was added
  without being scrubbed.
* An IOC that cannot find `lib<module>.so` at start is missing either the
  runtime dependency or its rpath entry.
